# Fixed package contents

B2.6 keeps labelled weight and pizza count together. `Product.packageContent` is optional and backward compatible; `packageContentSchema` in src/domain/package-content.ts stores the retailer-label source, product name, pack label, integer count and total weight in grams. The K-Ruoka and S-kaupat normalizers derive it locally from their existing catalogue names/pack labels. The development catalogue supplies the same evidence for its synthetic pizza. No extra source read, AI request or price-ratio inference is needed. src/stores/s-kaupat-pieces.ts remains the separate bridge for approximate weighed-piece ordering.

`pizzaPackageContent(name, label)` accepts a singular pizza with one readable package weight as one pizza, explicit integer kpl/pcs counts with total weight, or integer N x weight multipacks. Plural pizza names need an explicit count. Independently reported name/pack weights must agree; two explicit counts must agree. Mini pizzas, bases, dough, kits, portions, unsupported multipack wording, multiple weights and unclear counts cannot establish ordinary pizza contents. A readable mass alone never establishes a count for another food.

`packageAmount(product, unit)` validates the schema and re-derives those source claims before returning the count for a pcs request or weight for a g request. Count conversion also needs fixed per-item kpl/pcs retailer ordering; estimated weighed goods and kg sales are not fixed pizza packs. Missing or conflicting contents cannot bypass matching's unit guard. Existing explicit product wording, exclusions, accepted choices, availability and brand preference still apply.

`priceMetrics` uses that amount for whole-package rounding, payable totals, surplus and comparable unit value. Five requested pizzas need five one-pizza packages, three two-pizza packages or two three-pizza packages. Deposits remain part of payable totals; changing the shared price basis changes ranking by the same arithmetic. `match`, `purchasable` and `transferableLine` consume the same quantity facts. Service quoted pack edits and shopping quantity steps use the requirement's count/weight basis rather than dividing pizza count by grams. Alternative and review savings use `priceMetrics` too.

Persisted quotes retain optional package contents and revalidate them on restore. The transfer batch binding includes contents, and fresh review/transfer checks require those facts to stay unchanged. A changed count with the same package weight and price stops before writing. Retailer quantities stay absolute whole-package quantities; no checkout behavior changes.

Evidence: tests/pizza-packages.test.ts has 17 independent cases covering single/multi-pizza labels, rounding, split/conflicting source labels, unknown evidence, unsafe units, stock, brand/variety, both price modes, both actual adapter normalizers, retained quotes and changed-count review refusal. tests/ui/pizza-packages.spec.ts exercises real development IPC, quantity editing, SQLite restart, transfer and duplicate guards with zero AI calls. Existing price-ranking, piece-catalogue, quotes and matching checks passed (71 cases in the initial affected run); later parser/source-count changes passed their affected pizza cases. One existing quoted-pack edit case passed. Type checking, build and scoped formatting passed; no live retailer survey or release-suite claim.

B2.13 should preserve requested pizza/cube pieces and consume these normalized contents without inventing average item weights in interpretation.

## Stock cubes (B2.7)

`retailerPackageContent` is the shared normalizer entry point for both chains and development fixtures. It adds `stockCubePackageContent`: recognized Finnish liemikuutio names and English named stock cubes require explicit integer kpl/pcs or N x weight counts. A singular cube noun with only a package weight never means one cube. Powder, soup, sauce and liquid names do not establish cube contents. The same split-label consistency and persisted-fact validation apply. A 12 x 10 g package contains 12 cubes and 120 g; two requested cubes buy one package, while 13 cubes or 121 g buy two. Existing count-only labels retain their ordinary pcs pack normalization; no mass conversion is possible without evidenced mass.

`needsPackageCount` keeps gram-only cube products in the candidate list for pcs requests, with a pack-review reason after name, type and exclusion checks. It does not authorize purchase or skip pricing/unit validation. `Service.setPackSize` allows a known candidate's missing cube count to be confirmed in pcs and refuses another unit or a foreign product. It cannot replace verified count/weight contents. `applyPackSizes` applies the confirmed count to that product's pcs content while retaining its source name; the existing local packSizes state, quote validation and restart path preserve this explicit confirmation. No preference is saved.

Row details show an empty count field, fixed pcs unit and a visible request to confirm the cubes per package. They do not prefill the package's grams as a count. Confirmed counts can be edited in pcs and remain visible after restart. Bought and surplus amounts use the requirement unit: two cubes from a 12-cube package show 12 pcs bought and 10 pcs surplus, rather than comparing grams to pieces.

Evidence: tests/stock-cube-packages.test.ts has 14 cases for independent count/weight labels, unknown/conflicting/non-cube labels, actual K/S normalization, stock and unit/type refusal, enough-package count/weight conversion, refused overrides of verified facts, explicit missing-count confirmation and restart. Combined cube/pizza checks passed 31 cases; affected cube/matching/quote checks passed 52. One real Electron cube case passed explicit blank-count confirmation, correct bought/surplus units, SQLite restart and transfer of one package; the existing generic pack-size Electron case also passed. Build/type checking, scoped formatting and diff checks passed. Tests used temporary development data, zero live AI calls and synthetic catalogue facts. Live label coverage and release validation remain separate.
