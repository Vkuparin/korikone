# Local operation metrics

F16.6 records bounded counters in `metrics:operations`, separate from AppState, price observations and backups. The newest 100 entries survive restart. Diagnostics include only schema-validated entries; unknown fields, free text, unknown reasons and invalid numeric bounds are discarded. There are no prompts, notes, recipes, product/store/account identifiers, model names, receipts, prices, raw history, error text or request output in these entries. They are local diagnostics, not remote telemetry, and have no main-screen trace.

`src/application/metrics.ts` exports `operationMetricSchema`, `OperationMetric`, `OperationCounters`, `readMetrics`, `unresolvedReason`, `METRICS_KEY` and `METRICS_LIMIT`. Each entry has a fixed kind (interpretation, recipe-import, pricing, planning), outcome (success, failed, cancelled, obsolete), latencyMs, aiCalls, repairCalls, payloadCharacters, searches, resolverCalls and a bounded unresolved-reason count map. Counts are integers from 0 to 1,000,000; payload characters are capped at 100,000,000 and measured latency at 600,000 ms. Monotonic elapsed time excludes metrics persistence. No operation identifiers or timestamps are stored.

`Service.measureOperation(kind, callback)` gives the callback its own counters and records the result even on failure/cancel. `recordOperation(input)` rejects malformed records and serializes metrics writes separately from state writes, so pricing inside a context save cannot deadlock. Metrics read/write failures cannot change the application result or its original error. `operationMetrics()` reads sanitized local records for diagnostics or the fixture evaluator.

Main's real note and recipe-import handlers record inference calls and bounded repair counts through the pinned `InferenceSession`. `session.payloadCharacters` counts submitted prompt characters across actual dispatches, without retaining those prompts. Discovery failures record zero inference calls. Current interpretation/import have at most one repair; subsequent calls are therefore counted as repair there. The future coordinator must distinguish task/resolver/repair calls itself rather than treating all additional operation calls as repairs.

Every actual retailer candidate read is counted via `CandidateSearchOptions.onSearch`, immediately before the external search, including failures and expanded queries. Pricing records unresolved reasons using the same helper as the F16 evaluator. These are separate task/pricing spans, not a claim that the unfinished coordinator already has one complete planning-operation metric. F16.9–F16.11 can use the planning kind and explicit resolverCalls counter with their settled lifecycle; current production resolver use remains zero. Metrics never authorize a match or transfer.

`EvaluationResult.operationMetrics` exposes the same redacted records through `evaluateShoppingCase`. Coverage/SKU/quantity expectations remain independently authored; safe pricing and an operation success do not imply complete intent coverage. Fixture reports can compare measured calls, repairs, payload, search counts and reasons without storing any note or canned reply in an application profile.

Focused checks: `tests/operation-metrics.test.ts` covers both real adapters/tasks, repair, failure/cancel/obsolete, restart/bounds, hostile records, storage failures and actual expanded-search counts. `tests/ui/operation-metrics.spec.ts` uses real generation/repair/approval, isolated SQLite restart, diagnostics preview and local export; only native dialogs select the local test file. Existing focused diagnostics and context-save checks retain redaction and safe persistence. No live requests or retailer accounts are used.
