# Shared price ranking (B2.22)

The owner chose one price basis for both chains: lowest normalized unit value by default, or lowest payable total for enough packs. A 500 g requirement chooses the 1 kg pack at EUR 3 in unit mode (EUR 3/kg), but the 500 g pack at EUR 2 in total mode. The better unit value costs more upfront in this example.

## Schema and arithmetic

`stateSchema.priceBasis` is `"unit" | "total"`, default `"unit"` for old profiles and backups. `priceBasisSchema` and `PriceBasis` live in `src/domain/price-ranking.ts`. This is independent of `productPreference` (price/store brand/avoid store brand), exclusions and saved category preferences.

`priceMetrics(requirement, product)` returns verified `packs`, `payable` cents, surplus in the requirement's base unit, an `estimated` flag and an exact `unitValue` ratio, or null when price/quantity evidence is unusable. A unit value is `{ numerator, denominator, unit: "kg" | "l" | "pcs", estimated }`; divide only for display. Product-value ratios exclude refundable deposits; payable totals include them. Mass/volume content is normalized to kg/l; `pcs` means individual content, not a package sticker price. Package increments use enough whole order steps. Fractional counts/package increments cannot authorize piece packages. Piece-order estimates use explicit average weight and whole pieces; unsupported mass/volume ordering remains an estimate, not a transfer quantity.

`compareUnitValues` uses integer cross multiplication and returns null for unrelated units. `compareProductPrices` and non-mutating `rankProductPrices` compare the selected basis, then enough-pack payable cost, surplus and stable code-unit product identity. Missing or conflicting pack/price/deposit evidence cannot confer a best-value claim. If payable arithmetic is known but a unit ratio cannot be represented safely, `unitValue` is null and `fallback` is `"unknown-unit"`; label it unknown, not best unit value. Missing pack content is not guessed from prices.

Eligibility remains `candidateSuitability` / `selectableCandidate` in `src/domain/matching.ts`. Exclusions, explicit/category requirements, availability, remembered rules, soft brand preference and accepted product choices are applied before automatic ranking. `priceAlternatives(requirement, selected, candidates, options)` uses those eligibility rules and the same soft brand tier, filters improvements in the chosen basis and returns sorted automatic alternatives. It does not approve pending/unsafe replacements. `comparePriceAlternative` returns verified current/proposed metrics, exact `unitComparison`, `payableDelta`, `improves` and `benefit` (`lower-unit`, `lower-total`, `unknown-unit` or null). Use these for filtering and truthful badges; do not use a naked comparator as a suitability check.

The existing normalizers supply `Product.price` as the currently quoted product price and a separate deposit. The helpers do not manufacture another discount from optional campaign/regular/30-day metadata or an F11 personal offer. Public catalogue prices already quoted by the adapter remain usable. No current ordinary-product contract supplies verified quantity/loyalty redemption for conditional discovery offers; meeting an arbitrary pack count alone cannot activate those prices. Optional conditional or expired campaign claims do not override the current source price. No model price, unknown redemption, personal eligibility or bundle count is inferred.

`pieceQuote` / `approximateCost` are now implemented in `src/domain/product-price.ts`, with their existing planner exports retained. `matchRequirement` accepts `MatchingOptions.priceBasis`; planner `match` takes an optional fifth argument after exclusions, defaulting to unit mode. Service pricing, coordinator planning and provisional-line validation pass the state setting.

## Settings, saved quotes and UI handoff

`Service.setPriceBasis({ priceBasis })` and real `setPriceBasis` preload/IPC persist only the local setting. Invalid input/storage failure leaves the setting unchanged. There are no AI, catalogue or retailer-write calls. Ordinary `save` has the same behavior. A mode change keeps the shopping revision, selected products, quote and approval intact, while sorting cached alternatives locally; it invalidates an unfinished planning run. The next explicit generation/repricing uses the new basis. Manual choices still win.

Each `BasketLine.priceBasis` records the basis used to select that saved row. `persistedQuoteSchema` retains it and `restoredQuote` recomputes eligibility/arithmetic with it. Old quotes without the field use the previous total-cost policy. The mutable setting is deliberately absent from `pricingKey`; changing it cannot discard or rerank the current selected list after restart. Restored alternative ordering uses the current setting.

B2.23's files are `src/ui/settings-sections.tsx`, `src/ui/shopping.tsx`, `src/ui/details.tsx` and FI/EN copy. Add one shared Stores option using the IPC above. Use `priceAlternatives` for automatic cheaper suggestions and `comparePriceAlternative`/`priceMetrics` for selected/proposed display, replacing the existing independent `cost(p) < line.total` filter/sort. Pass context, current source note, category preferences, exclusions, product preference and price basis. Unit mode must find lower unit values even if payable totals increase. Show unit value, necessary packs, payable cost/delta and estimated/unknown status. Use Lower unit price / Edullisempi yksikkohinta when only unit value improves; show checkout savings only when payable totals actually decrease. Changing the control alone must keep current selections; test explicit repricing separately.
