# Portable category preferences

F15.3 implements explicit portable memory using the accepted [category policy](category-policy.md) and [shared matcher](matching-contract.md). Stored rules apply on both chains; product IDs remain separate store-specific choices. Review and Advanced controls remain F15.12/F15.13.

## Schema and migration

`src/domain/preferences.ts` exports `categoryPreferenceSchema` / `CategoryPreference` and `categoryPreferencesSchema`. The single-rule schema remains re-exported from `src/domain/matching.ts` for F15.2 callers.

`AppState.categoryPreferences` is an empty-by-default array of at most eight unique categories. A strict rule is `{category, qualifiers:[{kind,value}], strength:"required"|"preferred"}`. It requires at least one unique, category-applicable qualifier using `qualifierValues`. Eggs have no supported type qualifier yet. No retailer IDs, note spans, confidence, provenance fields, labels or purchase data belong in storage. Invalid or duplicate rules fail validation rather than disappearing silently.

Profile version stays 1. Old profiles and backups without the field load an empty array; current backups include the exact rules. Explicit backup import may restore them, including clearing them when restoring an older file. Ordinary `Service.save` rejects changed rules with `preferenceActionRequired`, preventing unrelated profile forms, interpretation or recipe approval from creating or deleting memory. It can preserve unchanged rules while saving other fields.

## Explicit actions

The following Service methods are exposed by main handlers and preload under the same names. Their strict input schemas and corresponding input types are exported from `src/domain/preferences.ts`.

| Method                       | Input                                               | Behavior                                                                                                                                                                                                                                                                                                                                                |
| ---------------------------- | --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `rememberCategoryPreference` | `{revision, requirementKey, productId, preference}` | The current quoted row key is `${id}:${unit}`. The actual candidate must have positive evidence for every saved qualifier, the same category and context, compatible quantities and no hard conflict/exclusion. Creates or replaces that category's rule and explicitly chooses that SKU for this list. Unknown or invented facts cannot be remembered. |
| `editCategoryPreference`     | `{revision, preference}`                            | Replaces an existing rule after an explicit save. A missing category fails with `preferenceMissing`. The supported type can be unavailable; matching then stays unresolved. It never invents a substitute or silently weakens Required.                                                                                                                 |
| `forgetCategoryPreference`   | `{revision, category}`                              | Removes that rule and returns matching to accepted defaults. A category without a stored rule is a no-op.                                                                                                                                                                                                                                               |
| `resetCategoryPreferences`   | `{revision}`                                        | Explicitly clears the portable array. It does not reset recipes, notes, appearance or other profile fields.                                                                                                                                                                                                                                             |

Schemas are `rememberCategoryPreferenceSchema`, `editCategoryPreferenceSchema`, `forgetCategoryPreferenceSchema` and `resetCategoryPreferencesSchema`; input types are `RememberCategoryPreference`, `EditCategoryPreference`, `ForgetCategoryPreference` and `ResetCategoryPreferences`.

Revision must match the current list or the action fails with `draftStale`. Active transfer/busy guards remain in force. Mutations validate and persist inside the existing serialized state queue. A failed state write preserves the state and quote. Successful changes advance revision, invalidate review/comparison and incompatible quotes, and refresh prices using local/provider reads. A failed refresh retains the explicitly saved rule and shows unpriced rows with the existing retry/error path.

Changes remove one-time SKU choices for currently represented requirements in the affected category across store bindings, preserving unrelated choices. Remember additionally records the explicitly selected current SKU. This prevents an old accepted substitution from silently bypassing a newly edited Preferred rule. Buying, accepting a SKU, dismissing review, parsing notes or importing recipes never creates a category rule.

## Matching, context and transfer

`MatchingOptions.preferences` carries the validated array. `matchingPolicy` selects the rule for the requirement's category; its existing singular `preference` option remains available for pure fixtures. Service pricing/acceptance, shopping cheaper suggestions and fresh transfer checks use the same portable rules. Explicit current-note qualifiers override matching remembered fields only for this operation. Generic requests do not erase rules. Unknown Required evidence stays rejected; unavailable Preferred evidence needs explicit one-time approval. Household exclusions remain mandatory.

`requirementQueryHints` in `src/domain/matching.ts` derives one fixed type-specific alias from effective required/preferred fields, combining milk/cream lactose and type when needed. Model-added specificity cannot produce a hint. `CandidateSearchOptions.queryHints` in `src/stores/candidates.ts` places bounded hints after the original query and before category aliases. The original query remains first; total reads remain at most three, deduplication stays in force and errors remain terminal. Service and fresh review/transfer/resume reads use the same hints, so a stored type can be retrieved even when the generic result page misses it.

`pricingKey` now uses matching version 2 and binds the rule array. Old quote bindings and changed rules cannot restore incompatible choices. Current SQLite quotes retain summaries without new catalogue reads after restart. State/backup rules contain no quote or SKU data, and diagnostics omit them.

`ContextState` permits `categoryPreferences`; `taskSnapshot` copies only this array and the previously whitelisted context fields. `buildCompactContext` validates at most eight portable rules from state or its explicit options, then adds remembered provenance to the category and each qualifier while retaining Required/Preferred strength. Observed summaries keep their separate maximum-20 boundary. No raw receipts, prior note spans, account data or purchase records enter this memory payload. Task output cannot write preferences; even a text response with an unsolicited top-level memory array leaves saved rules unchanged.
